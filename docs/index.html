The launch checklist for AI-built apps

The tool checks what it can see in your code. This list covers the rest. Tick items as you go: the ticks stay in this browser only.

1. Security: before anyone else uses it

  • Row Level Security is on for every Supabase table in the public schema, with a policy per action. Check Dashboard > Advisors > Security Advisor; fix every "RLS disabled" item. Supabase RLS guide
  • Only the anon / publishable key is in the browser. The service_role key and every AI or payment secret live in server code or Edge Functions.
  • No policy uses true for insert, update or delete. Writes are tied to the user: with check (auth.uid() = user_id).
  • Firebase: rules are not in test mode; reads and writes require request.auth.
  • .env is in .gitignore and was never committed. If it was, rotate every key in it: deleting the file does not remove it from git history.
  • User uploads sit in a private storage bucket and are served with signed URLs.
  • Sign-up has email confirmation or a CAPTCHA, so bots can't create thousands of accounts.
  • Test as a stranger: open the app in a private window, log in as a second user, and try to see or edit the first user's data by changing IDs in the URL.

2. Money: so a bug can't empty your account

  • A monthly spend limit is set at every AI provider (OpenAI, Anthropic, Google) and on your hosting.
  • Every route that calls a paid API checks the user and has a per-user rate limit.
  • Billing alerts go to an email you read.
  • You know which free-tier limit you will hit first (database size, function calls, bandwidth). Free Supabase projects pause after a week without activity.

3. Data: can you recover from a mistake?

  • The database schema lives in the repo (supabase db pull), so you can rebuild it.
  • You have a backup you have actually restored once, or you know your plan's backup window.
  • Error tracking (Sentry or PostHog) is on, so you hear about crashes before users leave.

4. Launch basics: so people can find and share it

  • The page title says what the app does, not "Vite + React" or "Lovable App".
  • Meta description, a 1200×630 share image (og:image) and your own favicon.
  • robots.txt and a sitemap, submitted in Google Search Console and Bing Webmaster Tools.
  • A custom domain when you can afford one; it builds more trust than a platform subdomain.
  • Analytics, so you know where visitors come from and where they drop off.

5. Legal pages

  • A privacy policy page: what you collect, why, which services process it, how long you keep it, and how to ask for deletion. App stores and Google sign-in require one.
  • Terms of service, linked next to it.
  • If you have EU users, a cookie notice for non-essential cookies; if you collect data in India, the DPDP Act applies. This is not legal advice: check your own case.

6. App stores

  • Google Play: new apps and updates must target Android 16 (API 36) since 31 Aug 2026. Google's rule
  • Google Play: new personal developer accounts must run a closed test with at least 12 testers for 14 days before production. Recruit real testers early; buying fake ones breaks Play policy.
  • Google Play: the Data safety form matches what the app really collects.
  • Apple: the app does more than wrap a website (Guideline 4.2), isn't a near-copy of another app (4.3), and has no broken screens (2.1). Apple's guidelines
  • Every iOS permission prompt explains in a full sentence why it is needed.

7. The first users

  • One sentence says who it is for and what problem it removes. If you can't write it, fix that before launching.
  • Watch one real person use it without helping. Fix where they get stuck.
  • Go where your users already ask for help (a forum, subreddit or group) and answer their questions; mention the app only where it truly answers one.
Paste-ready prompt for your AI builder: "Here is a safe-to-ship report for this project. Fix every critical and high finding exactly as described, without changing unrelated code, then list what you changed."

Questions

Does it upload my code?

No. It runs on your machine and only reads the folder you point it at. There is no telemetry.

Is a clean result a guarantee?

No. It is an automated check of your code, not a penetration test. A clean result means these checks passed; it does not prove the app is secure.

Can I run it in CI?

Yes: add uses: Shivamkole1969/safe-to-ship@v0 to a GitHub Actions workflow. See the README.
